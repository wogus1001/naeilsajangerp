# Platform Sequential Development Roadmap

## 목적

FC ERP의 다음 개발을 아래 순서로만 진행한다.

1. 전자결재 운영 완성
2. 가맹운영 일정·결재·알림 통합
3. 점주 포털과 본사 업무 자동화
4. 플랫폼 안정화·감사·관측 체계

각 단계는 구현, 자동 검증, 브라우저 QA, 문서 갱신, 커밋, dev 검증, 운영 확인까지 완료해야 다음 단계로 넘어간다. 선행 단계에서 발견된 차단 이슈는 다음 단계로 넘기지 않는다.

## 순차 개발 규칙

### 단계 상태

각 단계는 다음 상태 중 하나만 가진다.

- `대기`: 선행 단계가 완료되지 않아 개발하지 않는다.
- `계획 확정`: 요구사항, 데이터 변경, 테스트 범위가 확정됐다.
- `개발 중`: 해당 단계 전용 브랜치에서 구현 중이다.
- `검증 중`: 기능 구현이 끝나 자동 검증과 실사용 QA를 진행한다.
- `완료`: 완료 게이트를 모두 통과하고 운영 반영 여부를 기록했다.
- `차단`: SQL, 외부 계정, 승인 템플릿 등 외부 조건 때문에 완료할 수 없다.

### 브랜치와 커밋

- 단계마다 최신 `origin/main`에서 `codex/<stage>-YYYYMMDD` 브랜치를 새로 만든다.
- 서로 다른 단계의 구현을 한 브랜치나 한 커밋에 섞지 않는다.
- 구현과 직접 관련된 테스트는 같은 커밋에 포함한다.
- SQL migration은 코드와 함께 작성하되 적용은 사용자가 직접 한다. 최종 보고에 반드시 `SQL 등록 필요` 또는 `SQL 등록 완료 확인`을 적는다.
- 단계 완료 전에는 후속 단계의 제품 코드를 수정하지 않는다. 공통 결함이 후속 단계까지 영향을 주더라도 현재 단계의 완료 범위에서만 수정한다.

### 공통 완료 게이트

다음 항목을 모두 만족해야 단계 상태를 `완료`로 바꿀 수 있다.

1. 요구사항과 제외 범위가 문서에 확정돼 있다.
2. 관련 단위·API 테스트가 통과한다.
3. `npx tsc --noEmit --pretty false --incremental false`가 통과한다.
4. `npm run lint -- --quiet`가 통과한다.
5. `npm run build`가 통과한다.
6. 데스크톱 1440px과 모바일 390px에서 주요 사용자 흐름을 직접 확인한다.
7. 콘솔 오류와 가로 넘침이 없다.
8. 권한별 접근, 교차 회사 접근 차단, 실패 상태 안내를 확인한다.
9. `franchise-current-status.md`, `franchise-dev-qa-log.md`, 필요 시 `release-management.md`를 갱신한다.
10. 커밋·push 상태와 dev/main/운영 반영 여부를 기록한다.

## 1단계: 전자결재 운영 완성

### 2026-07-14 진행 기록

- 문서함 검색을 현재 페이지 한정 방식에서 회사 전체 조회 결과 기준 서버 검색으로 전환했다.
- 제목, 기안자, 소속 부서, 양식명, 문서번호를 함께 검색하고 상태 및 제출·수정 기간을 조합해 조회한다.
- 검색 조건 변경 시 첫 페이지로 이동하며, 늦게 끝난 이전 요청이 최신 검색 결과를 덮지 않도록 요청 순서를 보호한다.
- 표준 자동 탐색 명령 `npx tsx --test` 전체 707건, TypeScript, lint, production build를 통과했다.
- 실계정 브라우저에서 문서함 검색·상태·기간·페이지네이션과 390px/1440px 배치를 확인한 뒤 1-5 완료 여부를 판정한다.
- 1-6 보정으로 결재 일정 수신자를 미처리 원 결재자와 같은 회사의 활성 임직원 대결자로 다시 계산하고, 처리 완료한 병렬 결재자의 일정 노출을 제거했다.
- 공용 `/schedule`에서 결재 일정을 누르면 결재 문서 상세로 이동한다. 1440px/390px mock-session 브라우저 QA에서 이동과 가로 넘침 0건을 확인했다. 가맹운영 일정은 별도 사용자·저장소 정책에 따라 결재 일정과 연동하지 않는다.
- 최신 보안 리뷰 migration과 신규 `supabase_company_approvals_workflow_schedule_fix_migration.sql` 적용 후 2명 순차 결재, 병렬 합의, 대결 실계정 QA를 수행해야 1-6을 완료로 판정한다. **SQL 등록 필요**.

### 목표

현재 `/approvals` v2 기반을 실제 회사 조직에서 사용할 수 있는 전자결재로 완성한다. 사용자는 양식을 선택해 문서를 작성하고, 회사 구성원으로 결재선을 정하고, 여러 결재자가 순서대로 처리하며, 첨부·PDF·이력·알림을 한 흐름에서 사용할 수 있어야 한다.

### 현재 기반

- 전자결재 홈, 작성, 결재 대기, 내 문서함, 부서 문서함, 양식 관리, 조직·결재 설정 화면이 있다.
- 조직 단위, 구성원 소속, 직책, 부서장, 결재 역할, 기간형 위임 구조가 있다.
- 순차 결재, 병렬 합의, 참조·수신, 반려, 회수, 재상신 버전 구조가 있다.
- 구조화 필드 renderer, A4 미리보기, PDF, 비공개 첨부파일 흐름이 있다.
- 결재 단계 일정과 인앱 알림 연결 기반이 있다.

### 1-1. 운영 데이터 준비와 권한 기준 확정

구현 범위:

- 회사별 조직·팀·구성원 소속 현황을 조회하고 누락·중복·비활성 계정을 구분한다.
- 조직 편집 권한은 회사 관리자와 팀장 정책을 서버와 UI에서 동일하게 적용한다.
- 권한이 없는 사용자는 조직 편집 영역을 볼 수 없고 본인의 결재 위임만 관리한다.
- 조직 삭제 시 하위 조직, 구성원 소속, 결재 양식, 진행 문서에 미치는 영향을 사전에 보여준다.
- 진행 문서가 참조하는 조직은 삭제를 차단하고 보관 또는 구성원 이동을 안내한다.

완료 기준:

- 관리자, 팀장, 일반 직원, 비활성 직원, 다른 회사 직원의 접근 테스트가 있다.
- 조직 변경 후에도 이미 제출된 문서의 결재선 스냅샷이 바뀌지 않는다.
- 조직 삭제 실패가 내부 오류가 아니라 사용자가 이해할 수 있는 안내로 표시된다.

### 1-2. 결재선 설정 UX 완성

구현 범위:

- 문서 작성 2단계에서 `결재선 설정`을 열어 회사 구성원을 검색·선택한다.
- 결재, 합의, 참조, 수신을 한 화면에서 구분한다.
- 순차 결재자는 여러 명을 추가하고 드래그 또는 위·아래 버튼으로 순서를 변경한다.
- 병렬 합의는 `전원 동의`와 `1명 동의` 규칙을 분명하게 표시한다.
- 중복 대상, 자기 결재, 비활성 구성원, 다른 회사 구성원은 선택할 수 없다.
- 자주 쓰는 결재선을 개인 또는 회사 공용으로 저장하는 기능은 본 단계 후반 백로그로 둔다. 기본 결재선만으로 운영이 가능하면 1단계 완료를 막지 않는다.

완료 기준:

- 1명, 2명 이상 순차 결재와 병렬 합의가 실제 문서 단계로 생성된다.
- 현재 단계 대상자만 처리할 수 있고 단계 건너뛰기가 차단된다.
- 대결 기간에는 대리자가 처리할 수 있으며 원 결재자와 대리자 정보가 이력에 함께 남는다.

### 1-3. 양식 선택과 작성 흐름 정리

구현 범위:

- 작성하기 첫 화면은 양식 목록과 검색·분류 필터를 먼저 보여준다.
- 양식을 선택한 뒤 문서 작성 단계로 이동한다.
- 양식 기본 정보, 문서 항목 편집, 결재선 확인을 단계형 흐름으로 분리한다.
- 분류, 필드 유형, 권한 문구는 모두 사용자용 한국어로 표시한다.
- 2열 절반 필드는 같은 행에서 높이와 기준선을 맞추고 홀수 필드는 다음 행 전체 너비 또는 명시적 절반 너비로 처리한다.
- A4 미리보기는 다중 페이지를 모두 이동·확인할 수 있고 페이지 경계에서 필드가 잘리지 않아야 한다.

완료 기준:

- 품의서, 지출결의서, 계약보고서, 일반 업무보고 기본 양식으로 작성·임시저장·재진입이 가능하다.
- 양식 버전 변경이 기존 임시저장·제출 문서의 구조를 바꾸지 않는다.
- 모바일은 단일 열로 작성하고 데스크톱은 A4 결과를 함께 확인한다.

### 1-4. 첨부·PDF·문서 상세 완성

구현 범위:

- 첨부파일 선택, 드래그 추가, 파일명·용량·업로드 상태, 개별 삭제를 제공한다.
- 허용 형식, 파일당 10MB, 최대 5개 제한을 선택 시점과 서버에서 동일하게 검증한다.
- 임시저장 첨부와 제출 버전 첨부의 소유권·정리 정책을 명확히 한다.
- 문서 상세에서 권한 확인 후 첨부 다운로드가 가능하다.
- PDF는 한글 폰트, 표, 금액, 체크리스트, 결재선, 처리 이력, 다중 페이지를 지원한다.
- 처리 이력은 기본 접힘 아코디언으로 표시한다.

완료 기준:

- 허용 파일 업로드·다운로드와 제한 파일 거절을 확인한다.
- 작성자, 현재 결재자, 참조자, 부서 문서함 권한이 첨부·PDF 접근에도 동일하게 적용된다.
- PDF 다중 페이지에서 내용 누락, 겹침, 빈 페이지가 없다.

### 1-5. 문서함과 처리 상태 완성

구현 범위:

- 결재 대기, 기안, 결재, 참조·수신, 반려, 임시저장 문서함을 분리한다.
- 문서번호, 제목, 기안자, 부서, 양식, 상태, 기간 검색을 제공한다.
- 반려 사유는 필수이며 재상신 시 이전 버전과 변경 이력을 보존한다.
- 첫 결재 처리 전 회수만 허용한다.
- 최종 승인 후 수신 부서 확인 또는 업무 완료 처리 상태를 분리한다.
- 보존 기한과 보안 등급은 목록과 상세에서 같은 명칭으로 표시한다.

완료 기준:

- 동일 문서가 사용자 역할에 맞는 문서함에만 노출된다.
- 중복 action 요청에도 단계, 이벤트, 일정, 알림이 한 번만 생성된다.
- 반려·회수·재상신·최종 승인 이력이 시간순으로 정확히 남는다.

### 1-6. 전자결재 알림·일정 운영 QA

현재 상태: 코드 보정 및 일정 딥링크 브라우저 QA 완료, 신규 SQL 적용과 다중 사용자 실계정 QA 대기.

구현 범위:

- 상신 시 현재 결재자에게 인앱 알림과 결재 일정이 생성된다.
- 단계 완료 시 다음 결재자에게 일정과 알림이 이전된다.
- 반려, 회수, 최종 승인, 수신 확인 시 작성자와 필요한 대상에게 알림을 생성한다.
- 일정과 알림을 클릭하면 `/approvals/documents/[id]`로 이동한다.
- 알림톡은 승인된 템플릿·시나리오가 있을 때만 선택적으로 발송하고 결재 저장을 막지 않는다.

완료 기준:

- 2명 순차 결재와 병렬 합의 시나리오를 실제 브라우저에서 끝까지 처리한다.
- 일정·알림 중복이 없고 처리 완료 후 승인 대기 일정이 남지 않는다.
- 알림톡 설정이 없거나 실패해도 인앱 결재 흐름은 정상 완료된다.

### 1단계 필수 테스트

- 390px/1440px 양식 선택, 작성, 결재선 설정, 상세, 문서함 QA.

## 2단계: 가맹운영 일정·결재·알림 통합

### 진입 조건

- 1단계가 `완료` 상태다.
- 전자결재 문서 ID, 상태, 현재 처리자, 완료 이벤트 계약이 확정돼 있다.
- 결재 일정·알림 중복 방지 규칙이 운영 QA를 통과했다.

### 목표 범위

- 정보공개서 D-day와 수령 미확인.
- 업체 계약 D-30/D-7, 갱신·종료 처리.
- SV 방문, 보고서 제출·승인·반려.
- 오픈 준비 예정일과 미완료 업무.
- 점주 문의와 체크리스트 완료 요청.
- 수동 공유 일정과 개인 일정.

### 핵심 산출물

- 원천별 `source_type`, `source_id`, 상태 전이 표준.
- source upsert와 완료 동기화의 단일 helper/RPC.
- 오늘 일정, 이번주 일정, 승인 대기, 지연 일정 화면.
- 담당자·관리자 알림 escalation과 하루 1회 제한.
- 원천 저장 실패와 일정·알림 실패의 복구·재처리 정책.

### 완료 기준

- 각 원천의 대표 업무가 가맹운영 일정에 중복 없이 표시된다.
- 일정 완료가 원천 상태와 모순되지 않는다.
- 지연 판정과 KST 날짜 경계가 테스트로 검증된다.
- 다음 단계가 사용할 점주 이벤트 계약이 확정된다.

## 3단계: 점주 포털과 본사 업무 자동화

### 진입 조건

- 2단계가 `완료` 상태다.
- 점주 이벤트가 본사 일정·업무 큐로 들어가는 공통 계약이 운영 QA를 통과했다.

### 목표 범위

- 교육자료·매뉴얼 라이브러리.
- 정산·영수증·증빙 제출.
- 시설 문의와 반려 재제출의 자동 업무 생성.
- 체크리스트 미완료 리마인드와 본사 현황 집계.
- 공문·시정요청·계약 문서 수령 확인.
- 점주 활동 리포트와 본사 처리 SLA.

### 핵심 원칙

- 점주 계정은 `profiles`와 분리하고 자기 운영점만 접근한다.
- 점주 제출이 핵심 운영 데이터를 직접 덮어쓰지 않는다.
- 본사 확인·보관·완료 상태를 거쳐 원천 데이터에 반영한다.
- 알림톡 실패는 제출 저장을 막지 않는다.

### 완료 기준

- 점주 제출부터 본사 처리, 일정 완료, 점주 결과 확인까지 한 흐름으로 이어진다.
- 회사·운영점·점주 간 교차 접근이 차단된다.
- 파일 업로드·다운로드·삭제가 비공개 Storage 정책을 따른다.
- 모바일 390px에서 주요 흐름을 완료할 수 있다.

## 4단계: 플랫폼 안정화·감사·관측 체계

### 진입 조건

- 3단계가 `완료` 상태다.
- 전자결재, 일정, 점주 포털의 주요 상태 전이와 이벤트 종류가 확정돼 있다.

### 목표 범위

- 공통 감사 이벤트와 관리자 조회 화면.
- API 요청 ID, 사용자·회사·원천 ID 기반 로그 상관관계.
- 실패율, 지연, 중복, 권한 거절, 알림 실패 지표.
- 중요 workflow 재처리와 dead-letter 운영 절차.
- 보존 기한, soft delete, 복구, Storage 정리 정책.
- 정기 권한 회귀, secret scanning, dependency 취약점 점검.
- 대표용 운영 KPI와 장애 대응 runbook.

### 완료 기준

- 주요 실패를 사용자 제보 전에 관리자 화면 또는 로그에서 찾을 수 있다.
- 상태 변경 주체와 이전·이후 값이 감사 이력에 남는다.
- 재처리해도 문서, 일정, 알림이 중복되지 않는다.
- 장애 대응과 복구 절차를 다른 작업자가 문서만 보고 수행할 수 있다.
