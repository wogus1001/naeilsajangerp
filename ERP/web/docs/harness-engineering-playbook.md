# FC ERP Harness Engineering Playbook

## 목적

이 문서는 AI가 FC ERP를 예측 가능하고 안전하게 개발하도록 작업 환경을 설계하는 기준이다. 프롬프트를 길게 만드는 대신 프로젝트 구조, 필요한 맥락, 작업 계약, 실행 방식, 검증, 개선 루프를 명시한다.

세부 제품 정책과 최신 상태는 기존 문서를 계속 원본으로 사용한다. 이 문서는 제품 요구사항을 복제하지 않고, 해당 문서를 어떻게 찾아 읽고 작업할지를 정의한다.

## 6개 축

### 1. 구조: 어디에서 무엇을 다루는가

- `AGENTS.md`는 저장소 전체 지도와 금지사항만 유지한다.
- `ERP/web/AGENTS.md`는 Next.js 앱의 공통 구현 규칙을 담당한다.
- 도메인별 상태와 정책은 `ERP/web/docs/`의 전용 문서를 원본으로 사용한다.
- 기능 코드, 테스트, SQL, 운영 문서는 기존 소유 경계를 따른다. 단일 작업 때문에 새로운 최상위 폴더나 중복 추상화를 만들지 않는다.
- 기능 개발은 `codex/<topic>-YYYYMMDD` 브랜치 또는 격리된 worktree에서 수행한다.
- `.env*`, 인증 정보, 생성 산출물, `ERP/web/handoff.md`, 관련 없는 `.omo/*`는 작업 범위에서 제외한다.

### 2. 맥락: 필요한 정보만 필요한 시점에 읽는다

모든 작업의 공통 시작 문서는 다음과 같다.

1. `AGENTS.md`
2. `ERP/web/AGENTS.md`
3. `MAC_CONTEXT.md`
4. `ERP/web/README.md`
5. `ERP/web/docs/franchise-current-status.md`

그다음 작업 종류에 맞는 문서만 추가로 읽는다.

| 작업 종류 | 추가로 읽을 문서 |
|---|---|
| 제품 방향·다음 단계 | `franchise-growth-roadmap.md`, `platform-sequential-development-roadmap.md` |
| UI·카피 | `DESIGN.md`, `.omd/preferences.md`, 관련 화면 코드 |
| QA·회귀 | `franchise-dev-qa-log.md` |
| 커밋·배포 | `release-management.md` |
| 문서 정리 | `documentation-agent.md` |
| 보안 사고 | 해당 incident response 문서 |

규칙 파일에 구현 이력이나 긴 제품 설명을 누적하지 않는다. 같은 설명이 여러 문서에 생기면 현재 상태, 상세 이력, 운영 규칙 중 하나를 원본으로 정하고 나머지는 링크만 남긴다.

### 3. 계획: 작업 계약을 먼저 정한다

UI, API, SQL, 권한, 외부 연동 또는 여러 파일에 걸친 작업은 편집 전에 아래 작업 계약을 짧게 확정한다. 요청이 충분히 명확하면 에이전트가 합리적인 기본값으로 작성하고 바로 진행할 수 있다.

```text
작업 계약
- 목표:
- 포함 범위:
- 제외 범위:
- 원본 데이터/정책:
- 위험 요소: 권한, SQL, 외부 발송, 삭제, 배포
- 완료 조건:
- 검증 방법:
```

완료 조건은 `잘 동작`처럼 쓰지 않는다. 예를 들어 `작성자와 팀장만 삭제 가능`, `390px/1440px 가로 넘침 0`, `관련 테스트·tsc·lint·build 통과`처럼 관찰 가능하게 작성한다.

모호함이 결과에 영향을 주면 구현 전에 질문한다. 반대로 기존 코드와 문서에서 안전하게 확인할 수 있는 내용은 사용자에게 다시 묻지 않는다.

### 4. 실행: 가장 단순한 방식부터 선택한다

- 1~2개 파일의 국소 변경은 메인 세션에서 직접 처리한다.
- 서로 독립적인 조사나 검증만 병렬화한다.
- 설계, 구현, QA가 긴밀히 상호작용하는 대형 작업에서만 팀 실행을 고려한다.
- 하위 에이전트는 역할과 산출물을 명확히 지정하고, 결과를 회수한 뒤 바로 종료한다.
- 기존 패턴을 먼저 복제하고, 중복이나 복잡도를 실제로 줄일 때만 새 추상화를 추가한다.
- 긴 작업은 계획, 구현, 검증, 문서, 커밋 준비 순으로 상태를 갱신한다.

작업이 완료 조건에 미달하면 임시 예외로 덮지 않고 `계획 -> 실행 -> 검증` 루프로 돌아간다.

### 5. 검증: 만든 관점과 확인하는 관점을 분리한다

위험도가 있는 변경은 구현자의 자기 확인만으로 끝내지 않는다. 별도 리뷰 패스나 리뷰 에이전트에 다음 관점을 부여한다.

- 요구사항 누락과 상태 전이 오류
- 회사·역할·작성자 범위 및 교차 회사 접근
- 기존 API/데이터 호환성
- 실패·빈 상태·SQL 미적용 상태
- 모바일/데스크톱 레이아웃과 실제 상호작용
- 테스트 누락, 문서 드리프트, 비밀정보 포함 여부

#### 변경 유형별 최소 검증

| 변경 유형 | 최소 검증 |
|---|---|
| 문서만 변경 | 문서 diff 확인, 링크 확인, `git diff --check` |
| 순수 로직·API | 관련 테스트, 권한/오류 경로, `tsc`, `lint`, `build` |
| UI·사용자 흐름 | 관련 테스트, `tsc`, `lint`, `build`, 1440px·390px 브라우저 QA, console error 확인 |
| SQL·RLS·Storage | SQL 정적 검토, 중복 적용 안전성, 회사/역할 권한 검토, 적용 후 API/live QA |
| 외부 연동 | 미설정·실패·성공 상태 분리, 비밀정보 노출 점검, 실제 발송은 사용자 승인 후 수행 |
| 배포 | `release-management.md`의 Fast Release Runbook, dry run, dev 확인, 운영 도메인 READY와 smoke 확인 |

SQL은 사용자가 직접 적용한다. SQL이 추가되거나 바뀌면 최종 보고에 반드시 `SQL 등록 필요` 또는 `신규 SQL 없음`을 명시한다.

삭제, 운영 배포, 외부 메시지 발송, 인증 키 변경처럼 되돌리기 어렵거나 외부에 영향을 주는 작업은 명시적 승인과 가능한 dry run을 먼저 거친다.

### 6. 개선: 반복을 규칙과 도구로 바꾼다

- 같은 수작업이 3회 반복되면 스크립트, 테스트 helper 또는 스킬 후보로 기록한다.
- 같은 실수가 3회 반복되면 가장 좁은 범위의 `AGENTS.md`, 테스트 또는 운영 문서에 예방 규칙을 추가한다.
- 규칙을 추가할 때는 기존 규칙과 중복되거나 충돌하지 않는지 먼저 확인한다.
- 사용하지 않는 문서, 규칙, 하위 에이전트, 임시 산출물은 정리한다.
- 기능 마감 시 코드 변경뿐 아니라 QA 결과, SQL 적용 여부, 미검증 리스크, 배포 상태를 해당 원본 문서에 반영한다.
- 규칙이 계속 늘어나면 새 규칙 추가보다 원본 통합과 삭제를 우선한다.

## FC ERP 작업 게이트

### 시작 게이트

- 현재 브랜치와 worktree 변경 상태를 확인했다.
- `origin/dev`, `origin/main` 기준을 확인했다.
- 사용자 변경과 작업 금지 파일을 식별했다.
- 관련 원본 문서와 구현 파일을 읽었다.
- 작업 계약의 완료 조건과 검증 방법이 정해졌다.

### 구현 게이트

- 회사 범위, 역할, 작성자 권한을 서버에서 검증한다.
- SQL 미적용·외부 서비스 미설정 상태가 앱 전체 오류로 번지지 않는다.
- 기존 데이터와 API 호출자의 호환성을 확인한다.
- 사용자 문구는 내부 키나 개발 용어보다 실제 업무 용어를 사용한다.
- 관련 없는 리팩터링과 메타데이터 변경을 포함하지 않는다.

### 완료 게이트

- 작업 계약의 각 완료 조건에 근거가 있다.
- 변경 위험에 맞는 자동 검증과 브라우저 QA를 수행했다.
- 독립 리뷰에서 발견된 중요 문제를 반영했다.
- `git diff --check`와 staged diff/stat을 확인했다.
- 변경 문서, 검증 결과, 커밋·배포 여부, SQL 필요 여부를 보고할 수 있다.

## 컨텍스트 전환 기준

다음 중 하나면 수동 압축 또는 새 세션 인계를 권장한다.

- 하나의 기능 마일스톤이 끝나고 다른 도메인으로 이동한다.
- 긴 명령 출력이나 이미지 검토가 누적되어 초기 요구사항 확인이 어려워졌다.
- 이미 끝난 디버깅 대화가 현재 판단보다 더 많은 비중을 차지한다.
- 같은 사실을 다시 찾거나 설명하는 일이 생긴다.
- 계획, 구현, QA 중 두 단계 이상을 마쳐 다음 단계의 입력을 짧게 고정할 수 있다.

같은 작업을 이어갈 때는 아래 내용을 문서 또는 새 세션 첫 메시지로 넘긴다.

```text
- 목표와 현재 단계
- 브랜치·최신 커밋·worktree 상태
- 변경 파일과 핵심 결정
- 완료한 검증과 실패한 검증
- SQL·환경변수·외부 설정 상태
- 남은 작업과 다음 완료 조건
- 읽지 않거나 수정하면 안 되는 파일
```

## 적용 원칙

Harness는 규칙을 많이 만드는 작업이 아니다. 에이전트의 자유도는 유지하되, 데이터 손실, 권한 누락, 운영 오배포, 비밀정보 노출처럼 실패 비용이 큰 영역만 구조적으로 제한한다. 새로운 절차는 실제 반복 문제를 해결할 때만 추가하고, 기존 절차보다 단순한지 주기적으로 재평가한다.
